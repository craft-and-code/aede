# Aède DSP

`aede-dsp` processes decoded audio samples. It has no decoder, audio device, terminal interface, network access, or dependency on the catalog. The first stage accepts finite, interleaved `f32` PCM and applies one gain to every channel of a frame. Gain can change smoothly across calls, and is used by the local playback stream for metadata normalization.

The gain stage measures sample peaks and counts samples above full scale without clipping, so later DSP stages retain floating-point headroom. Before playback, `gain_with_headroom_db` caps a requested normalization gain using the declared ReplayGain peak or a measured true peak; when neither exists, it assumes a full-scale peak. `Dsp::process_for_output` includes a final `protect_output` call, which hard-clamps any unexpected samples outside [-1, 1] before output and reports how many it changed. In-range samples are untouched. This sample-peak policy does not guarantee true-peak safety or replace a perceptually designed limiter. The crate does not control system volume. `aede-core::playback::normalization` chooses a gain from ReplayGain or Opus R128 tags; this crate applies it without knowing its source. The [`loudness` module](src/loudness.rs) measures integrated programme LUFS and true peak from decoded PCM with the Rust `ebur128` crate. It accepts blocks and format changes without knowing files, tags, or the catalog. `aede-core` consults FlacCompagnon results, tags and caches to choose an available gain without predecoding a selection. It observes original source PCM during playback to cache missing track or complete-programme measurements for a later listen, outside the audio decode loop. The current gain stays fixed; `aede-dsp` applies it without knowing its source. Integrated LUFS remains available at 192 kHz and above, while true peak is deliberately unknown there because the meter no longer oversamples.

The processing and output-guard calls allocate no memory. Invalid samples, incomplete frames, and gains that would overflow `f32` are rejected before the buffer or gain ramp changes. The sample rate and channel count are fixed per `Dsp` instance; create a new one on a format change.

`OutputMeter` observes complete guarded PCM blocks after `Dsp::process_for_output`. Its snapshot reports submitted frames, sample peak before and after the output guard, an oversampled true-peak estimate, and the number of samples changed by the guard. The estimate uses `ebur128` and is unavailable at 192 kHz and above, where that library does not oversample, or if metering fails. These measurements describe PCM submitted to the sink before any CPAL integer dither or device conversion; they do not measure the physical output. The meter allocates outside the real-time audio callback. The CLI prints its snapshot and the actual processing stages for each track. The same meter can be used by a future remote audio route.

`ToneControls` provides optional broad bass and treble shelves, each limited to ±12 dB. The `biquad` crate implements the W3C Audio EQ Cookbook shelf coefficients with a monotonic slope and one state per channel; coefficients and state are prepared outside the PCM processing call. A flat setting removes the filters for an exact bypass. A boost reserves a conservative preamp of the sum of positive shelf gains, in addition to the existing peak-aware normalization cap. The final output guard remains necessary for transient overshoot and inaccurate peak metadata. The shelves use 120 Hz and 4 kHz midpoints at ordinary sample rates, lowered when necessary to stay below Nyquist. `Dsp::set_tone(ToneControls::FLAT)` resets to bypass; configure a new tone between streams because replacement clears filter state.

This establishes the sample contract, gain and broad tone stages, and a 24-band spectrum analyzer for terminal visualization. `aede-core::playback::stream::PcmTrack` supplies progressively decoded, processed PCM blocks and format metadata independently of the output destination; `aede-core::playback::Queue` holds the playing order. The `aede play` command sends these blocks to a CPAL device stream with a matching channel count and converts the sample rate when needed. If no compatible floating-point or integer output exists, it uses ffplay. It records listening history and shows animated bars in an interactive terminal. Matching-format tracks reuse the output and `aede-core::playback::session::PcmSession` retains tone and compatible rate-conversion state across their natural joins. Track-attributed spans keep delayed converter frames under the correct gain and listening identity. Physical gapless playback has not been measured on hardware. Playback applies ReplayGain or Opus R128 tag gain by default: album gain for a catalogued album selection, track gain for other selections. `--normalize off|track|album` overrides this. `--bass DB` and `--treble DB` apply the tone controls; both default to zero for flat bypass. A future remote server handler can use the same PCM blocks, gain/headroom functions and tone controls to transmit processed audio to the client device; no server audio route exists yet. Driving the in-memory queue remains future work. More detailed equalization, spatial processing, and other optional effects remain later stages.

## Device-rate conversion

`RateConverter` uses Rubato's fixed-ratio, bandlimited FFT conversion for ordinary rate pairs and sinc conversion for unusual ratios when the selected output rate differs from the decoded sample rate. It preserves state across input blocks, removes filter startup delay, drains the tail at the end of one uninterrupted stream, and emits the exact rate-adjusted frame count. The core playback session spans compatible successive files, preserving converter state and rounding cumulative frame boundaries once across the group. A matching-rate path bypasses it. Conversion runs on the decoding thread before gain and tone processing; the final output guard therefore runs after conversion. The native CPAL output chooses a supported format/rate, while ffplay receives the decoded rate. For integer-only devices, the final CPAL callback quantizes the guarded PCM with continuous TPDF dither. Signed and unsigned 8-, 16-, 24- and 32-bit formats are supported. Floating-point sinks bypass quantization and dither, while callback underrun silence remains exact digital silence.

## Final integer conversion

`TpdfQuantizer` adds two independent uniform draws in each sample’s least-significant-bit units before rounding. Its private, deterministic state continues across callback blocks and naturally advancing tracks that share an output stream. Conversion clips only to the chosen integer range after Aède’s earlier sample-peak guard. Aède does not claim a bit-perfect integer path: audio is decoded to `f32`, and the current native output deliberately dithers when converting that stream to integers. The ffplay fallback receives `f32le` and performs any device conversion outside Aède. A future remote transport can use this same quantizer only if it selects integer PCM.

## Channel mapping

`PcmFormat` retains an explicit channel mask when speaker positions are known; a channel count alone remains marked unknown above stereo. `StereoDownmixer` accepts conventional 2.1, 3.0, 3.1, quad, 4.0, 5.0, 5.1, 7.0 and 7.1 masks in the WAVEFORMATEXTENSIBLE/Symphonia channel order. It folds center and surround speakers into left/right using the -3 dB coefficients illustrated by ITU-R BS.775, omits LFE, and conservatively scales each stereo row so coherent full-scale channels do not overload the result. The 7.1 side and rear pairs each use -6 dB before the final row scaling. Unrecognized layouts are refused rather than assigned guessed positions. The matrix has no processing latency and allocates nothing per block.

`PcmTrack::open_stereo` applies this mapping to recognized multichannel sources while retaining the original source format for diagnostics or a future server transport. The local CLI uses that path before its shared gain, tone and output guard. FFmpeg fallback decoding currently has no trustworthy speaker mask for more than two channels and is refused for stereo downmix; mono and stereo remain supported. A future remote handler can choose the original PCM with its mask or the same stereo downmix, then transmit the selected format to the receiving device.
