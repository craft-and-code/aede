# Accounts and sessions

## Implementation boundaries

[`aede-accounts`](../../crates/aede-accounts/README.md) owns stable account identities, roles, password and API-key verification, credential generations, and validation of the independently versioned credential document. It has no catalog, filesystem or HTTP dependency. Its JSON documents contain private verifiers and belong only in protected persistence or backups, never in public account responses.

`aede-core::accounts` retains the storage adapter: native paths, bounded reads, private-file and opened-descriptor checks, atomic writes, and conversion to the existing catalog JSON representation. It reexports the account types for existing callers. Favourites, playlists and listening history remain in the core's personal store; the legacy `local` owner, account format 1 and backup format 3 are preserved.

`aede-server` owns bearer-session lifetimes, authentication admission, authorization of HTTP operations, and revocation checks during requests and media transfers. Clients configure and present these operations through the documented API.

## Behaviour

Accounts share one catalog. Favourites, ratings, notes, listening history, counts and collections remain scoped by the authenticated account's stable owner ID. A request cannot select another owner. The operating-system owner remains trusted: the CLI can manage accounts without an HTTP session, and existing CLI personal commands continue to use `local`.

The first account is an administrator whose owner ID is `local`, preserving existing personal data without rewriting `user.json`. Other accounts receive generated immutable IDs. Login names can change without changing ownership. Disabling an account keeps its personal data and prevents authentication. At least one administrator must remain enabled. There is no public registration or email-based recovery; the local operator can reset credentials.

Local CLI initialization, creation and password reset use masked terminal entry with exact confirmation. Explicit `--password-stdin` reads a redirected line for scripts without confirmation; it refuses a terminal. Neither transport takes passwords as arguments or prints them. Input is bounded by the domain's byte limit. Prompts go to stderr, preserving machine-readable stdout. Input occurs before the writer lock; mutations then reload credentials under that lock and recheck domain rules so concurrent changes cannot be overwritten by a stale snapshot.

Masked entry adds no Rust dependency. Unix uses the existing scoped `stty` guard and a strict UTF-8 reader; Windows uses borrowed console handles and key events through an isolated, documented Win32 FFI boundary. Echo remains disabled across both entries. Navigation events never become password characters; input translation and flow control cannot silently change a password. Cleanup discards buffered and queued input before restoring the original mode, including after cancellation or a rejected paste. A cleanup failure prevents credential publication; if cleanup cannot recover, echo stays disabled instead of exposing queued secrets.

There are three persisted roles. An `admin` manages accounts and installation work. A `user` can browse the shared catalog and read or change only their own personal data. An `auditor` is read-only: they can browse the shared catalog and use `GET` or `HEAD` on their own personal routes, but cannot change personal data or their password, manage accounts, or run administration/jobs. Auditors can still sign in, inspect their session and sign out.

`accounts.json` is a separate versioned store, written atomically under the existing data-directory lock. Passwords use salted Argon2id v19 with 19 MiB, two iterations and one lane, following [OWASP password-storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). The hash policy is bounded when reading stored credentials. Passwords contain at least 15 characters and at most 1024 UTF-8 bytes; they are never CLI arguments, included in public account views or logged. Login names contain 1–64 ASCII letters, digits, dots, underscores or hyphens, require at least one letter or digit and compare case-insensitively. Account files and backups containing credentials require private Unix permissions. Existing personal stores retain their format and owner values.

The new authentication API exchanges passwords for opaque 256-bit session tokens, supplied subsequently in exactly one `Authorization: Bearer …` header. This first API targets explicit API clients; browser cookie transport belongs with a future application UI. Tokens are never accepted in URLs. Sessions are held only in bounded process memory, expire after 12 hours or 30 minutes of inactivity, and are revoked on logout, credential/role/status changes, explicit revocation or restart. Backup restoration rotates the account-store epoch to invalidate every previous session. Password work runs off the HTTP runtime with bounded concurrency; login attempts have bounded global and per-name rate limits, and unknown or disabled accounts return the same invalid-credentials answer after equivalent password work.

With no account store on first access in a fresh local HTTP process, the existing anonymous loopback catalog and opt-in administrative token keep working. Once that process has observed the store, catalog and WebSocket reads require a session or the installation's administrative token. A missing or unreadable account store then fails closed until the process stops. This latch is held only in process memory: restarting local HTTP without the store restores anonymous compatibility mode. An unreadable store fails closed even on first access. Existing connections must be rechecked for session expiry, account changes and activation of account mode. Administrative session holders may manage accounts and installation jobs. User sessions can browse the shared catalog and use only their own personal-data API. Auditor sessions can browse the shared catalog and read only their own personal-data API. The transitional administrative personal routes continue to address `local` explicitly.

The default HTTP listener remains loopback-only with Host/Origin checks. Explicit [HTTPS](../server/remote.md) requires accounts, a certificate/key and one exact public authority; it refuses legacy tokens and all remote administrative routes. Native clients can use the authenticated [PCM playback contract](../server/playback.md), which records only acknowledged playback for the session's owner. A web login screen and external identity providers remain future work. Target-device capacity still needs measured deployment validation.

The [Subsonic/OpenSubsonic adapter](../server/subsonic.md) authenticates with nonexpiring, individually revocable `id.secret` API keys. Each component has 256 OS-random bits; only the secret's bounded Argon2 verifier is stored. Optional `api_keys` records keep account-store format 1 backward-readable by this implementation without changing the catalog format. The same full key may be sent as `apiKey`, or in legacy `u+p` fields with its matching account name; the password field is a compatibility transport for a client key, not account-password authentication. It cannot recover passwords or support salted-MD5 authentication. Key metadata excludes owner/generation/verifier and secrets are disclosed only after successful publication. Maximum: eight per account, 512 total. The server caches at most 128 SHA-256 token fingerprints, while checking current key presence, owner, epoch and account generation on each request and during media. Native bearer sessions never become adapter keys.

Adapter favourites/ratings, static playlists and client-declared scrobbles use the same stable personal owner as native routes. Administrators receive no access to another account's private data. Mutations recheck current keys and roles under the shared writer lock before an atomic personal-store save; auditors can browse their own data and verified artwork but cannot mutate or start audio. Optional playlist/scrobble tables retain personal-store format 2, while legacy format 1 remains readable; static playlist IDs reveal no owner/path. Temporary now-playing declarations are process-local, visible only to their owner, expire and disappear when their key becomes invalid. They are not playback evidence or persisted listening events.

Account changes and account-wide revocation purge affected keys. Restoring credentials rotates the epoch and purges restored keys; a backup without accounts preserves the current credentials/keys. Revoking one key leaves other keys and native sessions valid; ordinary logout remains session-only. Key management stays with the trusted local CLI under the shared writer lock. The graph remains shared; adapter-specific browsing hierarchy and XML/JSON encoding belong to the server.

Backup envelope version 3 adds the independently versioned accounts store. Versions 1 and 2 remain readable, and their absent accounts part never deletes or replaces an existing account store. Sessions are never backed up. Resetting the rebuildable catalog preserves accounts.
