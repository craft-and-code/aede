# Roadmap

The status below reflects the current implementation. [Current state](../coding/current-state.md) records the verification checkpoints and deployment limits. An implemented feature still needs its stated client or hardware acceptance checks; this roadmap does not mark those checks complete merely because the software tests pass.

| Milestone | Implementation status | Remaining work |
| --- | --- | --- |
| M0 — catalog | Done and hardened | No blocking feature gap recorded in the current scope. |
| M0.5 — personal data and queries | Done and hardened | Listening quotas and account-specific album visibility are later extensions. |
| M0.6 — copying and conversion | Done and hardened | Continue platform/filesystem validation for release and target deployments. |
| M1 — identification and enrichment | Done and hardened | The owner has confirmed the live-service paths; retain that evidence in the [manual verification record](../coding/m1-manual-verification.md). |
| M2 — API and persistence | Implemented and hardened; deployment acceptance pending | Real-library and target-NAS CPU/memory budgets, client interoperability, service lifecycle and recovery validation. SQLite remains conditional on measurements. |
| M2.5 — client adapters | Subsonic/OpenSubsonic foundation implemented; compatibility incomplete | The local Submariner baseline is accepted. Validate other clients and add the missing methods listed in the [adapter guide](../server/subsonic.md#remaining-compatibility-work). Jellyfin is deferred. |
| M3 — playback | Local queue, seeking, repeat, uniform/smart shuffle, synchronized terminal lyrics/native lyrics API, decoded FLAC MD5, Windows console controls, compatible native remote joins and optional native seek/edit/checkpoint resume implemented; player scope incomplete | Native Windows console/output acceptance and physical local/remote gapless validation. |
| M4 — network audio devices | Started: finite SlimProto, UPnP AVTransport, OpenHome Playlist and experimental Google Cast profiles | Real-device acceptance, continuous joins, richer controls, shared device registry/authenticated API and optional additional transports. |

**Current priority: M4's first device profiles, with M3 output acceptance retained.** The owner has chosen to begin network-device integration after M3 software hardening. This does not establish the still-pending Windows console/output and physical gapless checks. The local Submariner artists/albums/audio/ratings/favourites workflow is accepted; every optional adapter endpoint remains separate work. The pre-extraction [Fix CI checkpoint](https://github.com/craft-and-code/aede/actions/runs/37237142050) passes on macOS, Linux and Windows with Rust 1.89; this does not establish real output acceptance. Docker/NAS deployment remains deferred.

**M0 — the catalog (done).** Scanning, graph model, statistics, diagnostics and command-line navigation are implemented. M0, M0.5 and M0.6 have received repeated code, security, performance, documentation and test reviews; the completed corrections and their limits are recorded in [current state](../coding/current-state.md).

**M0.5 — what the user writes, and how it is asked for (done).** Favourites, ratings, notes and free-form tags in one annotation store keyed so that a scan can never destroy them; play history and play counts; a real query grammar with ranges, negation and `OR`; saved queries; and export/import of the lot. Every one of those records carries an **owner** from its first version. The accounts now implemented alongside M2 reuse that ownership without replacing existing personal data. None of the local annotation/query work needs the network or a database. See [What the user writes](annotations.md#what-the-user-writes-favourites-ratings-notes-history), [several users](annotations.md#which-is-the-same-question-as-several-users) and [Querying](querying.md#querying).

**M0.6 — getting music out (done).** `aede copy`: a selection, written to a player or a card, keeping the tree it sits in. The selection is the query grammar's, so the command adds no filters of its own. What is settled and done: the tree, the companion files (with the catalog's own cover rather than an extension filter), name adaptation for FAT/exFAT probed rather than guessed, verification, resume, and the refusals — a destination that is missing, one inside the library, one without room. Conversion on the way out (`--compress`) drives ffmpeg as an external program, encodes only lossless sources, and carries the metadata across. See [Copying to a player](../copying.md#copying-taking-your-cdthèque-on-the-road).

**M1 — identification (done).** MusicBrainz for relations and credits, AcoustID/Chromaprint for badly tagged files, Cover Art Archive and Fanart.tv for artwork, Wikidata to reach the Wikipedia article in the user's language, and opt-in LRCLIB lyrics fetching. Also: country and formation dates, band line-ups as dated relations, release types, and the completeness report that says which albums are missing from the shelf. Matching retains confidence and explicit manual review/correction instead of blindly rewriting local identity or tags. The owner has confirmed AcoustID and Fanart.tv with API keys, successful lyrics fetching and fetching artwork for an album without a cover. See [Identification](identification.md#identification-m1) and the [manual verification record](../coding/m1-manual-verification.md).

**The canonical music graph programme before M2 is complete.** Its nine stages are implemented: audit, canonical objects, attributed identity/reconciliation, rich recording and work credits, typed bidirectional relations, dedicated navigation views, relational search, persistent and reversible quality resolution, then the local-first layer. Approximate matches and identity conflicts have an explicit `aede review` path and never become links by accident; relationships themselves can be annotated, the attributed graph exported, and personal corrections replayed from a small rules bundle. SQLite can therefore migrate a stable musical model instead of deciding its meaning. See [The canonical music graph](music-graph.md).

**A value from MusicBrainz sits _beside_ the tag, never on top of it.** An imported analysis is attributed to its source and never merged into Aède's own fields, which is exactly what lets `doctor` report that two methods disagree. Writing a MusicBrainz genre into the `genre` field would cost three things at once: saying where the value came from, noticing that MusicBrainz and the tag differ, and undoing it. And it would not even survive: a scan rebuilds the catalog from the files, so the tag would overwrite it on the next run. M1 therefore has its own attributed layer, carried across a rescan and removable, with the display choosing which to show.

**And the layer is kept whole, including where it agrees.** The tempting saving is to store nothing when MusicBrainz says what the tag already says. It is the wrong trade, for one reason: _agreement is information_. "Checked against MusicBrainz and it matches" and "never checked" are two different states, and a layer that only records disagreements cannot tell them apart — the same distinction the catalog already draws between a genre that exists and holds nothing and a genre nobody ever heard of. Keeping the answer whole also means the question "does my tag still match?" is answered **offline**, from the catalog, the day after you re-tag a file — where storing only divergences would send you back to the network to re-derive something you had already been told. The precedent is again in the codebase: raw tags are kept per file for exactly this reason, so the graph can be rebuilt without touching the disk. A few hundred bytes per release buys all of it.

**M2 — the API (implemented and hardened; deployment validation pending).** HTTP, JSON, catalog events, task activity, CLI-shaped navigation/inspection, personal data and bounded asynchronous scan/fetch jobs are implemented. Store-changing CLI commands delegate to the running server on Unix, and all writers share a data-folder lock. The route contract is documented in [API v1](../api.md) and the [server README](../../crates/aede-server/README.md). Current synthetic storage and HTTP measurements are recorded in the [M2 benchmark](../coding/m2-storage-benchmark.md), and the [server review](../coding/m2-server-review.md) records the security corrections. Real-library and target-NAS capacity, service startup/restart and recovery still need deployment acceptance. SQLite is a measured option, not a milestone obligation; see [Architecture](architecture.md#when-this-becomes-a-database).

**M2 — what Aède worked out about the bytes moves out of the catalog (done).** Integrity verdicts, fingerprints and imported analyses now live in `conclusions.json`, keyed by path, size and modification time. Legacy catalogs and version-1 backups migrate their embedded conclusions before the catalog is rewritten. A later bump of `store::FORMAT_VERSION` can therefore require a rescan without discarding hours of byte-level work. See [What Aède worked out about the bytes](conclusions.md).

**M2.5 — other servers' languages (Subsonic/OpenSubsonic foundation implemented).** The adapter supports revocable application keys, ID3 browsing/search, several album sorts, original-file audio with byte ranges, JPEG/PNG sidecar artwork, private favourites/ratings/playlists and client-declared scrobbles. Clients without an API-key field can use their account name and complete key through legacy `u+p`; account passwords and salted-MD5 tokens remain unsupported. Supersonic and Submariner setup is documented. Local authentication, artist/album browsing, original FLAC playback, ratings and artist/album favourites have been confirmed with Submariner 3.4 on macOS; other formats, optional panels, Supersonic and remote deployment still need real-client acceptance. Remaining compatibility includes some album sorts, legacy folder browsing and `getStarred`, rich information, embedded covers, queue/bookmark persistence, OpenSubsonic playback reports and on-demand transcoding. Unsupported requests fail explicitly. Jellyfin remains a later, timeboxed adapter. Both protocols translate over shared Aède domain rules, never a second core. See the [adapter guide](../server/subsonic.md), [Compatible Aède specification](../server/compatible-aede.md) and [interoperability design](interoperability.md#speaking-other-servers-languages).

**Accounts, HTTPS and native audio are implemented alongside M2.** `aede-accounts` owns identities, roles and credential policy; `aede-core` retains protected persistence, while `aede-server` owns HTTP sessions and authorization. Stable owners preserve existing personal data, salted Argon2id protects credentials, and admin/user/auditor roles constrain personal and installation work. Version-3 backups include accounts and restore invalidates sessions. Explicit [HTTPS](../server/remote.md) requires accounts and keeps administration local. The single-track and finite-queue [PCM contract](../server/playback.md) shares the decoder/DSP, bounds client buffering and records acknowledged playback for the authenticated owner. Subsonic/OpenSubsonic has separate application-key authentication and streams original encoded audio without DSP. Finite native queues now retain processing across compatible joins. Browser login/player UI and mobile-client acceptance remain work. See [Accounts](accounts.md) and the [HTTP reference](../server/accounts.md).

**M3 — playback (partly implemented).** The [M3 software hardening review](../coding/m3-review.md) records decoder/source identity, numerical safety, bounded work, spectrum timing and measured converter improvements; output acceptance remains separate. `aede play` provides three local policies: without-effects by default, explicit strict bit-perfect and DSP. Ordinary CPAL output has an ffplay fallback; strict glibc Linux uses an explicitly admitted direct ALSA hardware route. DSP retains metadata/measured normalization, bass/treble controls, device-rate conversion, integer dither, diagnostics and a spectrum display. Its in-memory queue drives repeat off/one/all, seeded uniform and metadata-based smart shuffle, initial source positioning and runtime ten-second moves. Unix terminals and native Windows consoles share single-key transport controls, with input-mode restoration and redirected-input handling; actual Windows console/output acceptance remains pending. Occurrences preserve intentional playlist duplicates; runtime order changes retain the played prefix and current audio. Smart uses genres and credits, keeps every occurrence and reports missing evidence or stylistic breaks. Opt-in `play --lyrics` follows local timed lines, using callback-consumed frames with native output and explicitly estimated timing with ffplay; plain text has a bounded preview and missing lyrics do not interrupt music. The native lyrics API supplies source/text/timestamps for clients following their own clock, independently of the unchanged PCM transport. Compatible local tracks share output and processing state; software tests verify frame counts and PCM joins, while physical gapless playback remains unmeasured. The [capture tooling](../coding/gapless-measurement.md) prepares whole/split probes and bounded idle/CPU/I/O trials; a suitable physical return cable is still needed before acceptance. Native PCM v1 accepts finite ordered queues, with cumulative client consumption and separate occurrence histories; compatible joins retain DSP/conversion state. Optional interactive native playback now adds seeking, future-tail editing and private account/profile checkpoints with explicit resume; epochs/reset acknowledgements keep discarded prefetched audio out of history. Real remote-client output acceptance remains open. Decoded FLAC MD5 verification now runs in the same playback decode and finishes at EOF; missing signatures and incomplete decoding establish no verified digest, while a mismatch is a decoding error. This runtime result is distinct from stored container checks and attributed FlacCompagnon analyses. Additional named shuffle modes (by album, spread, similar, journey and discover), local CLI live queue editing and local CLI session/resume behavior remain future designs. See the [play manual](../cli/play.md), [Playback](playback.md#playback-m3), the [DSP README](../../crates/aede-dsp/README.md) and the [DSP review](../coding/dsp-review.md#remaining-work-in-priority-order).

**M4 — network audio devices (started).** The standalone [`aede-devices`](../../crates/aede-devices/README.md) crate owns the controllers, with shared original-media policy reused by the server; the CLI calls it directly. `aede devices --bind IP` explicitly discovers UPnP/OpenHome renderers. `aede cast <selection> --protocol slimproto|upnp|openhome|googlecast --bind IP --device TARGET` supplies a finite ordered selection to one LAN device, preserving original encoded bytes. SlimProto uses explicit player connection and native-codec preflight; UPnP uses ConnectionManager/AVTransport; OpenHome uses its device playlist with explicit replacement permission. Google Cast adds explicit mDNS discovery, observed-certificate inspection and a certificate-pinned Default Media Receiver sender; replacement of an existing application also needs explicit permission. Temporary HTTP media is capability/peer restricted, separate from the catalog/admin API, and creates no assumed listening history. These are initial software profiles, with real-device acceptance pending. Continuous joins, complete controls, a persistent registry and authenticated remote commands remain work. See [Network audio devices](../server/devices.md).

### M4 responsibilities and candidate extensions

M4 includes discovery/selection, codec/rate/channel capability negotiation, explicit transport/volume policy, queue/position feedback, reconnect/failure handling, device identity/authorization and output evidence. Gapless and synchronized multiroom need physical measurements. Server DSP also needs an explicit compatible device transport rather than rewriting originals.

| Surface | Purpose | Priority/status |
| --- | --- | --- |
| SlimProto | Squeezebox/Squeezelite playback | First finite profile delivered; continuous joins/controls and real-device acceptance remain |
| UPnP AVTransport / OpenHome Playlist | LAN hi-fi renderers; on-device OpenHome queues | First finite controller profiles delivered; renderer/firmware acceptance pending |
| UPnP MediaServer / ContentDirectory | Let independent DLNA control points browse Aède | Natural next extension; a separate server role, absent from the renderer controller |
| Google Cast | Chromecast/Nest/Cast-capable audio equipment | Initial certificate-pinned sender and explicit mDNS discovery; real-receiver acceptance pending |
| AirPlay | Apple/AirPlay receivers | Candidate study with explicit sender/receiver/version and licensing boundaries |
| Snapcast bridge | Synchronized open-source multiroom | Candidate bridge to an existing Snapserver, preserving its synchronization engine |

The remaining candidate extensions are proposals, not approved dependencies or implementation commitments. [Google Cast](https://developers.google.com/cast/docs/overview) separates sender and receiver roles; [Cast audio-device guidance](https://developers.google.com/cast/docs/audio) adds device/app requirements. The first Aède Cast profile uses the Default Media Receiver, original-file URLs and exact receiver certificate pins; it does not claim Google certification, physical gapless or synchronized multiroom. [Apple's MFi FAQ](https://mfi.apple.com/en/faqs) lists AirPlay audio as a licensed accessory technology, which does not by itself decide the policy for every possible software sender. [Snapcast](https://github.com/snapcast/snapcast) provides an existing synchronized client/server engine. Bluetooth/local hardware output belongs to the client/device backend; a future MPD-shaped API would be a client adapter rather than a network-speaker protocol.

**Future Phémios device-control architecture.** Prefer server-driven playback: Phémios selects a speaker and sends authorized control requests to Aède; Aède on the server/NAS supplies audio directly to that speaker. The phone is a remote control and does not relay the audio. Before exposing this workflow, implement the shared device registry and authenticated API, ownership/conflict rules, account permissions, cancellation and transport feedback. Protocols remain in `aede-devices`; `aede-server` authorizes commands; Phémios presents selection and controls. Client-native AirPlay/Cast routing may coexist as a separate playback route. The current explicit CLI controllers do not yet provide this API.

**Lyrics.** Reading embedded lyrics and `.lrc` sidecars is implemented. LRCLIB fetching belongs to completed M1 and remains an explicit choice. M3 now supplies line-synchronized terminal display and a native read API for graphical clients such as Phémios; neither starts fetching or changes the audio stream. Word-level timing and user editing are separate extensions. See [Lyrics](lyrics.md#lyrics).

**Conversion and deployment.** Copy-time conversion through external ffmpeg is implemented and refuses output inside the library; on-demand adapter transcoding is separate, unimplemented work. See [Converting files](interoperability.md#converting-files). Release acceptance includes platform checks and a validated deployment procedure. A Docker/NAS guide exists, but the repository does not build or publish a container image; persistent mounts, permissions, startup ordering, host reboot and off-host recovery need target validation. See [Operating Aède](../operating.md#docker-image-on-a-linux-host-procedure-only).

RAAT and "Roon Ready" certification remain out of scope: no supported integration or certification programme is planned for Aède.

## Notes towards what comes next

The [transparent playback and bit-perfect contract](bit-perfect.md) defines a local native FLAC/WAV integer 16/24-bit mono/stereo baseline and separate source, software and digital-output acceptance. Typed sources, exact sessions/adapters and the strict queue share the existing transport, with consumption-based exact history. Local `play` exposes without-effects (new default), bit-perfect strict and DSP policies, device selection and discovery. Without-effects prefers the original rate and avoids native integer dither for exact values; DSP retains automatic album/track normalization and its processing policy. The first strict candidate is an explicitly selected glibc Linux ALSA hardware route with opened-parameter/control readback; CPAL and other platform strict routes remain refused. Per-device persistence and native PCM v1 stay unchanged. Pure simulations and synthetic Linux API checks do not establish native Linux compilation, linking or runtime. Those target-platform checks and digital-capture acceptance remain pending; software implementation does not establish physical bit-perfect output.

The remaining player designs are in [Playback](playback.md); missing adapter surfaces are in the [Subsonic/OpenSubsonic guide](../server/subsonic.md#remaining-compatibility-work). Target-device and physical signal acceptance are tracked in the [DSP review](../coding/dsp-review.md#remaining-work-in-priority-order).

Listening-time limits and administrator-controlled album visibility are discussed extensions, without an implemented policy yet. They must be enforced by the server if adopted. Browser/mobile interfaces and external-service sign-in remain separate design work. The [DSP product proposal](dsp-product-proposal.md) retains optional Premium effects as research, with no approved pricing, release date or implementation promise.
