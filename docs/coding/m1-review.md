# M1 hardening review

## Scope and method

The owner requested a new M1 review after the completed M0 checkpoint: identification, external enrichment, source provenance/reviews, sourced graph navigation and source-backed catalog projections. This first pass uses finite call-chain inventories and reproductions; it is not a claim that every M1 function or supported platform has been exhaustively verified. This first-pass record predates M0 integration; the later integration checkpoint below records its commits.

Reproductions use isolated temporary catalogs, copied/generated audio, offline source imports and canned or loopback HTTP responses. No real library, provider key, account session or music-provider quota is used. Nine demonstrated defects are grouped below into five call-chain families. Each correction has a failing regression before its production change, plus positive/negative controls. Fixture expectation corrections are not counted as product defects. Rust tests remain in sibling test files.

## Demonstrated defects

### Source-backed country exports ignored the requested window

With a scanned file and an imported identified French artist, `countries --offset=1 --limit=1` correctly omitted France in the terminal but still exported it in JSON and CSV. `list_countries` applied the window only to its human output. The export now applies the same offset and limit after the existing deterministic ordering.

The public CLI regression exercises multiple countries, supported numeric/name sort directions, JSON/CSV/file output, `--all` with an offset, an empty window and refused options. Read-only commands preserve catalog, source, personal and history bytes. Analogous artist-country, statistics-country and source listing/export paths were checked without another demonstrated defect. HTTP country/statistics paging already applies its own window; no client DTO change is required.

### A canonical work page omitted trusted sourced recordings

A three-recording fixture has two local work tags and a trusted source link for the third recording to that exact work MBID. `query work:ID` finds all three, and the third recording links back to the work, but the work page and Continue section showed only the two locally tagged recordings.

The canonical page now unites local recording IDs with trusted source links carrying the same work MBID, deduplicating canonical recordings. Pending, rejected and conflicting claims remain evidence; acceptance and undo retain their existing semantics. The underlying graph and tags are unchanged. The sibling regression includes multiple placements, spelling differences, a different MBID with the same title, and review transitions. Source-only and part-of-work navigation were inspected as analogues. HTTP `/works` remains its explicitly documented catalog-only projection; Phémios has no work page consuming this CLI result.

### Secondary enrichment misapplied source trust

Five related identity/retained-evidence decisions misapplied the shared trust rule:

- The labels pass promoted a `label_mbid` retained on a pending or rejected release claim into an exact label lookup. It now requires a trusted release claim; otherwise the label remains a scored name search.
- The Discogs fallback followed a pending or rejected MusicBrainz label identity, including from the online label page, and could publish a separate Discogs profile. It now refuses that path before provider requests or publication. Accepted matches retain their original score.
- The covers pass reused a saved Cover Art Archive front address without checking the artwork claim's review. A public source import followed by rejection still downloaded and published the rejected image. The shortcut now requires trust; independent local/trusted MusicBrainz identities keep their existing fallback behavior.
- A pending or rejected Wikipedia label biography suppressed an explicit Discogs fallback for an independently trusted MusicBrainz label. Both the batch and online label page now require a trusted Wikipedia biography before skipping Discogs; exact and accepted Wikipedia biographies still avoid the request.
- After accepting an approximate MusicBrainz label, its confirmed numeric Discogs lookup inherited the parent's approximate confidence. The new independent Discogs claim had no review and therefore remained hidden from the trusted native biography projection despite successful acquisition. It now carries `Identified` for its exact ID lookup; the MusicBrainz record, original score and review remain unchanged. No decision is copied to another source, and an explicit Discogs rejection still wins after refresh. Previously stored approximate profiles require an explicit refresh; there is no automatic cache migration.

The regressions check pending/rejected/accepted/exact states, request admission, retained source bytes and successful positive cases. The existing Discogs success fixture now explicitly accepts its approximate identity instead of relying on the bypass. Its profile/provenance checks are preserved; its old child-confidence assertion is corrected to describe the exact Discogs lookup. The parent's original confidence is independently checked unchanged.

### Malformed Wikimedia responses became permanent empty answers

An otherwise successful transport could return `{}` or malformed entity/sitelink/extract fields. The summaries pass treated that response as a genuine absence, writing an empty Wikipedia record and skipping a later ordinary retry; a forced refresh could also erase an existing biography and its attribution.

Entity and summary structure are now checked before recording success or absence. Invalid responses increment the pass's failure count, preserving memory/store bytes and retry eligibility. Valid empty sitelinks, readable empty/stub summaries, legacy string extracts and unambiguous entity redirects retain their behavior. The integration-through-pass regression checks both an initial fetch and a refresh with previously credited prose. Unknown summary types remain conservatively retryable failures rather than biographies or cached absences.

### Imported artwork identifiers could escape the asset cache

A public source import accepted an identified MusicBrainz artist record whose opaque source ID was an absolute path. For an artist without one shared folder, the fallback cache construction joined that ID onto `assets/artists`; the absolute component replaced the intended prefix. A real image could then be published outside the cache. The reproduction writes only to owned temporary directories.

The cache destination now validates a single ordinary identifier component and checks the existing cache hierarchy before artwork requests/publication. Artist and label asset callers share the same construction policy; malformed separators, dot components, absolute paths and NULs are refused. Existing opaque single-component IDs remain compatible. The server's artist-artwork fallback uses the same checked helper. Static symlink checks do not establish protection against a hostile process concurrently replacing directory entries; no stronger race guarantee is claimed.

### AcoustID recording metadata could erase an accepted identification

An `ok` result with a valid outer ID and score, but an object/string recording table or an unidentified recording row, was treated as a genuine miss. A forced refresh could replace a previously accepted recording claim and discard its precise review. The admission guard now refuses a present unreadable recording table before the identify pass can publish it. The [official response examples](https://acoustid.org/webservice) allow results without recording metadata, so absent metadata and an empty recording list remain valid misses; no UUID-format assumption is added.

The pipeline regression starts red with an object-valued table. It covers five malformed forms both before an initial lookup and after an accepted claim, preserves the in-memory layer and serialized bytes on failure, and verifies a successful retry and retained decision for the same identity. Existing service-error and key-redaction tests remain in force.

### Duplicate exact reviews made source trust depend on row order

A public source import with two decisions for the same `(entity kind, entity key, source, source_id)` tuple succeeded. Reversing only those rows changed whether a matched country claim appeared trusted, even when the rejected row had a newer timestamp. This is a snapshot admission ambiguity, not a request to change intentional decisions in separate imports.

Loading now refuses duplicate exact review keys, consistently with duplicate source snapshots. The existing `set_review` update behavior is unchanged. Core controls distinguish entity kind/key, source and optional identifiers, cover identical as well as contradictory duplicates, and retain version 1 migration. The CLI regression proves refusal before changing catalog/source/user/conclusion bytes, followed by a valid separate import that deliberately replaces a decision while retaining an expired Discogs profile and its attribution.

### Malformed MusicBrainz relationship lists became complete empty credits

Recording and edition lookups accepted non-array `relations` values or non-object rows as complete empty answers. The completed flag then suppressed an ordinary retry; a forced refresh could lose previously retained credits. The same problem applied to the relationship list of a linked work.

The recording/release admission boundary now checks the structure of the relationship lists it consumes before publishing a complete answer. Absent optional relations and valid empty lists keep their compatibility; unknown relationship families remain skippable. No new response-ID equality or redirect policy is imposed. Sibling parser and full-fetch regressions cover initial failure, successful ordinary retry, preserved refresh bytes, nested work relations and a genuine completed empty answer.

### Malformed Wikidata portrait answers became cached absences

The portrait pass independently called the permissive P18 selector without the summary pass's response validation. An empty success body or an unreadable present P18 table produced a saved negative result and suppressed the next ordinary run. Portrait-specific structural admission now runs before recording an absence or falling back to Fanart. A readable entity without a P18 claim remains a valid absence; preferred/ranked and unusable statements retain the existing selector behavior.

### Malformed Fanart tables suppressed artwork retries

A correctly identified Fanart artist or label body with object-valued image tables was accepted as having no images. The shared metadata request could consequently publish several negative family markers and prevent future ordinary attempts. The shared response validator now refuses wrong types for present supported image collections, including nested album artwork, before any family publication. The [official documentation](https://api.fanart.tv/) distinguishes v3.2 album arrays from the older object format; Aède explicitly requests v3.2. Absent collections and valid empty arrays remain supported; an entry without a usable image address remains skippable as before. The portrait and complete-artwork regressions exercise both initial acquisition and retained prior evidence.

### A portrait already on disk could trigger a redundant alternate-format download

With `artist.jpg` already present and a Wikidata PNG answer, the portrait pass still made two requests and added `artist.png`, despite its promise to leave existing portraits alone. The original JPEG was not overwritten; this finding concerns redundant requests/publication, not invented destruction. Both existing JPEG and PNG portraits now bypass the metadata request in ordinary and full portrait runs. The sibling regression verifies no provider request, no added alternate-format image and no new attribution record.

### An imported Unicode release date panicked during display

A supported source import containing a non-ASCII `first_released` string succeeded, then public `missing --all` exited 101 while slicing its first four bytes inside a UTF-8 character. The getter now uses a checked string boundary and returns no displayed prefix when that boundary is unreadable. It preserves the source date rather than rewriting or rejecting the complete document. The sibling regression round-trips the source layer and covers full/short/empty ASCII dates and both readable and unreadable Unicode boundaries. The new registry regression preserves the other source-aware commands, plus missing's independent list/forget actions. English/French manuals replace the old no-op guidance with the explicit refusal.

### Source-only artist pages ignored pagination outside one credit table

Counts and Continue links retain the complete matching set. The public integration regression covers JSON/CSV/M3U, empty windows, limit/all/offset combinations, ordering keys, complete counts/navigation, invalid zero limits and unchanged stores/audio.
