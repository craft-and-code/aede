# Parent-owned desktop engine

The ordinary server remains independent. An explicitly launched desktop parent may set `AEDE_DESKTOP_LEASE=1` and run `aede serve --port=0 --data=<isolated application store>`. This profile refuses file-based TLS options, fixed ports and non-loopback listeners; protocol 2 below accepts a private in-memory TLS identity. It neither discovers nor changes another installation.

The parent supplies one UTF-8 JSON line on stdin, bounded to 32 KiB, with `username`, `password` and only the optional `tls` identity described below. A new isolated store bootstraps its administrator and an empty catalog. A retained store must authenticate the same existing enabled administrator; corrupt stores and mismatched credentials are refused, never reset. The parent owns secret generation and protected storage. Credentials are not arguments or readiness output.

Readiness is one JSON line: `{"desktopProtocol":1,"address":"http://127.0.0.1:<assigned port>"}`. The parent retains stdin after bootstrap. EOF triggers the same graceful shutdown path as a termination signal; accepted jobs keep their normal drain semantics. A closed or crashed parent therefore releases its child without a global process search. Delegated job children remove the desktop lease environment so they cannot accidentally bootstrap or wait for a second owner.

Administrative JSON scans additionally accept `unavailable_folders`, with the same count, absolute-path and byte bounds as `folders`. These explicit roots skip traversal and retain previously catalogued files, even if an unmounted volume leaves an accessible empty mountpoint. Exclusions retain precedence. A subsequent scan without this declaration evaluates the mounted filesystem normally. The desktop host supplies OS mount evidence; Aède does not guess that every empty root is offline, mount network shares, or clear unavailable media. CLI delegated scan handling accepts this information only in the existing owned job profile.

The public `serve_with_options` Rust API remains unchanged. `serve_with_owner_lease` accepts an optional atomic owner-closed flag in addition to the same options.

## Encrypted owned bootstrap (protocol 2)

The same profile additionally accepts an optional `tls` object with exactly `certificate` and `private_key` PEM strings in its stdin bootstrap. The whole line is bounded to 32 KiB; each PEM is bounded to 8 KiB, with one matching certificate/key required before stores are created or a socket announced. The desktop parent generates this identity, retains only the public certificate as its explicit trust root, and never persists the key or sends it through browser IPC. Aède holds the identity in memory and configures HTTPS after binding its ephemeral loopback port. Protocol-2 readiness is `{"desktopProtocol":2,"address":"https://127.0.0.1:<assigned port>"}`. The parent must verify the certificate and loopback hostname for both HTTPS and WSS; it must never disable TLS verification or silently downgrade after failure. No system certificate installation or global trust change is needed. Protocol 1 remains compatible when no TLS identity is supplied; current Phémios requires protocol 2 for its owned engine.

The public `serve_with_desktop_tls` adapter accepts a validated in-memory `DesktopTls` identity and owner lifetime flag. It refuses fixed ports, non-loopback addresses and a second configured file-based TLS listener. HTTPS account administration requires a named administrator session; installation tokens remain unavailable. Closing stdin keeps the normal job-drain/lifetime contract under either protocol.
